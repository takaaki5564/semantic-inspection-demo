# NEDOデモ GUI改善案

2026-10-08時点の確認用設計案です。GUI実装にはまだ着手していません。今回の撮影同期修正を先に確認し、この案をレビューしてからDay 5へ進みます。nedo-v3の部位一覧を、基本GUIと同時に設計・実装する方針です。

## 画面で伝えること

画面だけで「何を検査するか」「どこまで観測できたか」「なぜ次の視点へ動くか」「画像が本当に保存されたか」を追えるようにします。アームの見た目だけで撮影完了を判断させない構成にします。

現在の失敗では、後方への到達が済んでも描画側カメラ情報が前方のままで、画像保存前に停止していました。GUIでは移動・撮影検証・保存・観測更新を区別し、保存前の画像や予測coverageを実観測として表示しません。

画面配置の案は[ワイヤーフレーム](GUI_IMPROVEMENT_PROPOSAL.svg)です。図中の数値はB/Y初回の実測例に基づく配置サンプルで、実行に接続したGUIのスクリーンショットではありません。

## 画面配置

| 場所 | 内容 | 目的 |
|---|---|---|
| 上部 | 部品A/B、仕様X/Y、仮想カメラ／UR10eの選択、初期化、1ステップ、連続実行、停止予約、reset | 実行条件と操作を一か所にまとめる |
| 左上 | 外部OverviewCameraによる3Dシーン | アーム・部品・カメラの移動を確認する。手先カメラの取付を画面操作で変えない |
| 左下 | 保存済みの最新RGBと撮影履歴の切替 | 前方／後方の見え方を比べる。原画像を既定とし、可視性点の説明画像は明示して切替 |
| 右上 | 現在の進行、終了理由、累積観測点数、撮影数、追加動作数 | 実行中・完了・blocked・failedを区別する |
| 右中央 | 部位ID・名称・状態・累積coverage・次の撮影対象 | nedo-v3の必須一覧。R1/R2を初回から両方表示し、仕様XのR2は対象外とする |
| 右下 | 次の動作、理由、撮影／保存状況、出力先 | R2の不足→後方撮影という因果と、画像保存の事実を伝える |

部位状態は「未確認／一部観測／観測条件充足／再確認必要／対象外」と表示し、必要に応じ内部状態名も併記します。色だけに頼らず文字と点数を添えます。`confirmed`を「良品」「検査合格」と言い換えません。累積coverageと、その1枚の可視点数も区別します。

原画像には撮影ID、視点名、実撮影時刻を添えます。次の画像の待機中も最後の保存済み画像を表示し、「前回画像」と明示します。まだ保存されていない`capture_01.png`を空欄のまま完了扱いにしません。

## 操作と画面の遷移

1. 部品・仕様・実行方式を選び、「初期化」で新しいセッションを作ります。部位は未確認、対象外部位は対象外、画像は未撮影になります。
2. 最初の「1ステップ」は初期視点の確認→移動→静止→撮影・保存→観測更新まで進めます。次の動作が必要なら、その計画と対象部位を表示して止まります。
3. 次の「1ステップ」は選択済みの動作を実行し、実観測まで更新して止まります。「連続実行」は同じ処理を停止条件まで繰り返します。
4. 必要点が揃ったら「観測条件充足」、追加手段がなければ`blocked`と理由、撮影や保存の整合性が崩れたら`failed`と理由を表示します。
5. 部品・仕様・方式の変更は実行中に反映しません。物理動作が停止した境界でresetし、新しい条件のセッションを作ります。旧画像・旧観測・旧計画を新しい条件へ混ぜません。

実行中の「停止予約」は現在の移動・撮影を終えた境界で止めます。衝突回避や実ロボットの非常停止機能としては扱いません。ウィンドウ終了・異常・時間上限の検出は既存の有限停止処理を維持します。

## 今回の欠落画像を見落とさない表示

| 状況 | 表示する内容 |
|---|---|
| 後方へ移動中 | `rearへ移動中`。前方の保存済み画像と累積66/126点を保持 |
| 目標到達、描画待ち | `静止確認済み・描画更新待ち 1/10`。2枚目は「未保存」、coverageを増やさない |
| 撮影の整合性確認済み | 撮影検証が済んだことを表示。保存完了とは区別 |
| PNG・必要な証拠の保存成功 | 保存済み画像と出力先を更新し、観測反映イベントの状態を表示 |
| 描画不一致が解消しない／保存異常 | `撮影失敗`または`保存失敗`と平易な理由。最後の有効な保存・観測結果を保持 |
| 必要な実観測が揃う | 観測条件充足。製品の傷や良否の判定は未評価と表示 |

詳細なカメラ行列や関節角は折り畳みの診断欄へ置きます。通常画面では「描画更新待ち」「目標に到達できない」「保存に失敗」のように、利用者が判断できる情報を優先します。今回追加した`render_synchronization`も診断の根拠として利用します。

## 実装の構成

既存の`FreeCameraExecutor`／`ArmMountedCameraExecutor`、評価器、プランナーを維持します。部位状態の定義は[部位可視化設計](REGION_VISUALIZATION_DESIGN.md)に従い、GUIは読み取った状態を表示します。

現行`run_camera_session`は一括実行関数です。ボタンごとに同じロジックを複製すると、CLIとGUIの計画・停止条件が分岐してしまいます。そこで次の実装段階で、既存ループを一つのコアセッション制御へまとめ、1ステップ実行と連続実行を同じ処理で実現します。既存関数は連続実行の互換入口として残します。

| 層 | 実装予定 |
|---|---|
| コア制御 | 1観測サイクルずつ進めるセッション制御。実観測・計画・停止条件を共有し、CLIとGUIで同じ結果を検証 |
| 評価器／状態 | 部位名称メタデータ、`InspectionRegionState`、有効観測の累積、対象外表示、セッション識別・reset |
| イベント／保存 | 移動、描画待ち、撮影検証、保存成功、観測反映、失敗を区別。保存成否と検査状態を同じ成功フラグにしない |
| GUI | インストール済みのIsaac Sim／`omni.ui`上で、概要・部位一覧・RGB・操作を表示。描画やボタン処理が物理を勝手に進めない構成 |
| レシピ候補 | 同じ実行記録から部品／仕様版、実視点、証拠、停止理由、未承認状態を保存。画像数だけで承認済みレシピにしない |
| 領域表示 | 一覧と同じ状態を消費する差替可能な表示。まずPrim単位の3D分離を検証し、短期に難しければGUI内の簡易立体図 |

GUIの更新は実行イベントから行い、前セッションの遅れたイベントを適用しません。計画上の次対象は`predicted_new_point_ids`で示しますが、予測値から観測済みcoverageを増やしません。失敗した撮影の観測・保存を、成功した撮影履歴へ追加しない境界を明確にします。

3D状態色のために元のR1/R2マーカーを塗り替えると検査RGBが変わります。このため、最初のGUIでは部位一覧とRGB表示を完成させ、その後に3D表示の分離を確認します。表示用Primが検査画像・影・評価三角形・物理へ混入しないことを実測できた方式だけ採用します。

## 実装・確認の順序

1. **今回：撮影同期の修正と検証。** 後方の2枚目を含む実RGB・実姿勢・保存結果を確認する。
2. **今回：GUI改善案のレビュー。** この画面案と部位状態の意味を確認する。GUIコードはこの段階では実装しない。
3. **Day 5最初の実装：コアの1ステップ制御と部位状態。** 既存CLIの結果を維持し、数値テストと保存出力で確認する。
4. **次の実装：基本GUI＋部位一覧＋RGB。** これらを同じ画面へ組み込み、両方式の実動作を確認する。レシピ候補の保存も同じセッション情報を使用する。
5. **次の表示段階：Prim単位の3D色分け。** 分離を短期に検証できなければ簡易立体図へ切り替える。両方は作らない。

この順なら、基本GUIを作った後に部位状態の仕組みから組み直す必要がありません。各段階の出力確認を挟みます。

## 受入条件

- B/Yで、初回R1が63/63、R2が3/63となり、後方撮影後にR2の累積が63/63へ更新される。撮影一覧と保存ファイルが対応する。
- A/Yは初回126点で終了し、B/XではR2を対象外と表示して初回63点で終了する。不要な追加動作を表示・実行しない。
- 1ステップと連続実行、CLIとGUIが同じ計画・実観測・終了理由となる。GUIの有無で検査RGBや物理が変わらない。
- 描画遅延、到達不可、動作禁止、上限、保存失敗をそれぞれ識別できる。未保存画像や予測結果で成功表示にしない。
- A/B・X/Y・方式切替とresetで、旧履歴・旧計画を持ち越さない。実行中の条件変更や連打で二重実行しない。
- 原画像と可視性説明画像の意味、現在画像と前回画像、累積観測と1枚の可視性が分かる。
- 3D色分けまたは簡易図が部位一覧と一致し、検査RGB・レイ判定・物理への表示混入を防げる。

新しいライブラリ、Webサービス、別アプリは導入せず、既存Isaac Sim環境で実装する方針です。画面改善後も欠陥検出精度、衝突安全性、実ロボット対応の実証は別工程です。
